Cloud Services - Assignment 6

Topic: CI/CD Automation, Observability & Health Probes

Part A: Theoretical Questions & Answers

1. CI/CD Pipeline vs. Manual Deployment

Manual Deployment: Developers manually build Docker images on their laptops, push them to a container registry, and run oc apply commands from their local terminal. This process is slow, error-prone, and relies heavily on human intervention.

CI/CD Pipeline: An automated cloud worker monitors the Git repository. Every time new code is pushed to the repository, the worker automatically runs tests, builds the container image, pushes it to Docker Hub, and triggers a rolling update on OpenShift without any manual work.

2. GitHub Actions Workflow Structure

A GitHub Actions workflow is defined in .github/workflows/deploy.yml and consists of three key concepts:

  • Triggers (Events): Specifies when the workflow runs (e.g., on: push to the main branch).
  • Jobs: A set of steps executed on a runner virtual machine (e.g., ubuntu-latest ).
  • Steps: Individual tasks executed sequentially, such as checking out code, logging in to Docker Hub, building the container image, and deploying to Rahti using oc CLI.

3. Observability: Metrics, Logs, and Traces

Observability provides deep visibility into a running application using three core pillars:

  • Metrics: Numeric data aggregated over time (e.g., "What is the average CPU and RAM usage of the backend pod?").
  • Logs: Timestamped text records of discrete events (e.g., "Which request path failed with a 500 internal server error at 12:30 PM?").
  • Traces: End-to-end tracking of a single request as it travels across multiple microservices (e.g., "Which backend microservice caused a 2-second delay during page loading?").

4. Liveness Probe vs. Readiness Probe

Liveness Probe: Checks if the container is still running. If the probe fails (e.g., due to an infinite loop or deadlock), OpenShift kills the container and restarts a new instance.

Readiness Probe: Checks if the container is ready to accept web traffic. If the probe fails (e.g., application warming up or database connection lost), OpenShift stops routing traffic to that pod by removing its IP address from the Service endpoints list until it recovers.

5. Secure Management of Secrets in CI/CD

Cluster passwords, registry access tokens, and API keys must never be hardcoded inside CI/CD workflow YAML files or committed to Git repositories. If exposed, malicious bots can steal credentials, compromise infrastructure, or generate massive cloud bills. GitHub Actions solves this by storing sensitive values in Encrypted Repository Secrets , which are injected securely at runtime and masked in execution logs.

Part B: Implementation & Verification Evidence

1. Automated CI/CD Pipeline

Every commit pushed to the main branch automatically triggers a GitHub Actions workflow that builds the backend image, pushes it to Docker Hub, and updates the deployment in CSC Rahti.

2. Structured Application Logging

The backend application outputs formatted JSON HTTP request logs, including request paths, HTTP methods, and response times. Live logs are retrieved directly using the OpenShift CLI command oc logs deployment/backend .

3. Readiness Probe Failure (Pod Status)

When the readiness probe path was intentionally set to a non-existent route ( /wrong-path ), OpenShift detected the failed health checks and marked the backend pod status as 0/1 READY .

4. Readiness Probe Failure (Endpoints Disconnected)

Because the backend pod failed its readiness probe, OpenShift immediately removed its IP address from the active backend Service endpoints list (showing <none> ), ensuring zero broken web traffic is delivered to end users.
